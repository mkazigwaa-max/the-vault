SQL: Postgres template scores view

create or replace view template_scores as
select t.id, t.name, t.segment,
count(s.id)                                    as sent_count, count(s.id) filter (where s.replied)           as reply_count, case when count(s.id) < 5 then null else round(count(s.id) filter (where s.replied)::numeric / count(s.id), 3) end                                            as reply_rate from templates t left join sends s on s.template_id = t.id group by t.id, t.name, t.segment order by reply_rate desc nulls first;

Build

sdr-find

Create a new skill called sdr-find.

Its job: stand up the three tables this system runs on, then keep Prospects

topped up without ever adding the same person twice.

FIRST RUN ONLY - build the tables:

1. Ask me which table layer I am using and connect to it. Check whether tables

called Prospects, Templates and Sends already exist. If they do, read their

REAL field names and option strings, tell me what you found, and skip to

"Every run" - do not recreate anything.

2. Ask me for my segment list: the two to four kinds of buyer I sell to, in my

own words. Use those exact strings, spelled identically, in BOTH Prospects

and Templates. Exact-match on this string is how the send step finds a

template. One stray space and a prospect drops out of the pipeline silently.

3. Create the three tables with the fields I have specified in the guide, using

my segment strings for both Segment fields and exactly these Stage options:

New, Enriched, Contacted, Replied.

4. Then three computed fields on Templates: Sent Count (count of linked Sends),

Reply Count (count of linked Sends where Replied is ticked), and Reply Rate:

IF({Sent Count} < 5, BLANK(), {Reply Count} / {Sent Count})

If my table layer's API refuses to create count, rollup or formula fields,

say so plainly and give me click-by-click instructions to add those three by

hand. Never fake them with a plain number column - a number you write is a

number that goes stale and lies to me.

5. Write the base id, the table ids, my exact segment strings and the exact

Stage option strings into a file called sdr-stack-setup.md, and tell me where

it is. Every other skill in this system reads that file first.

EVERY RUN - fill Prospects:

6. Ask me: job titles, company type, industry, size, location, and how many.

Default 25. Small on purpose - data credits are real money and a bad guess at

500 rows costs more than it teaches. If I have run this before, offer my last

search back and let me say "same again".

7. Search my prospect source LIVE, on this run. Never reuse a result set from a previous run or from setup day. The whole point of running this weekly is

that the world changed.

8. Require a work email AND a LinkedIn URL on every person. Skip anyone missing

an email rather than guessing one.

9. Before writing anything, read the existing emails out of Prospects and drop

any match. Dedupe on email, lowercased and trimmed - never on name or

company, which collide.

10. Write one row per new person: Name, Company, Title, Email, LinkedIn URL,

Stage = New. Leave Segment and Research Notes empty; the next skill fills

them. Read the Stage field's real options before writing, never from memory.

11. Report: how many added, how many skipped as duplicates, how many skipped for

a missing email. If the missing-email number is high, say so plainly - that

means my targeting sits outside my data source's coverage, not that you

should try the search again.

Rules: on most sources search is free and enrichment costs credits, so filter

down to the rows I am actually keeping BEFORE you enrich anything.

sdr-enrich

Create a new skill called sdr-enrich.

Its job: turn a row with a name and an email into a row someone could actually

write to - two lines of research, and a segment.

When I run it:

1. Read sdr-stack-setup.md. Find every row in Prospects where Stage = New. If

there are none, say so and stop. Do not go looking for something else to do.

2. Work them ONE AT A TIME. Batching is how three rows go missing without

anyone noticing.

3. For each person, find two things and nothing else:

a. ONE INTEREST. Something they have publicly signalled they care about - a

topic they post about, a group or newsletter they follow, a cause, a

sport, a school. From their LinkedIn profile if I have given you a

compliant way to read it; otherwise from anywhere else public - their

company blog, a podcast they went on, a conference bio, their X account.

b. ONE THING IN COMMON, only if I can actually verify it. A shared employer,

a shared school, a person we both know, a customer we share. If you

cannot verify it, leave it out. Never infer a relationship from a shared

industry, a shared city, or a shared connection count.

4. Write Research Notes as TWO SENTENCES maximum. One fact only true of this

person, plus the thing in common if there is one. "They opened a second

location in Austin and still run scheduling in a shared spreadsheet" beats

"a growing company focused on operational excellence". If everything you

found is true of anyone in the segment, write that you found nothing

specific - that is a real and useful answer, and it tells me my list is off.

5. Set Segment by picking one of the options ALREADY in the field. Read the

field's real options before you write; do not work from memory of setup day.

Never invent a new one. If none fit: leave Segment blank, tick Needs Review,

and tell me which prospect and why.

6. Set Stage = Enriched.

7. Report: how many enriched, how many flagged Needs Review, and which ones.

Rules: never write a connection you could not verify. The email that follows is going to say this out loud to a stranger, and being wrong about how you know

someone is the fastest way there is to get a genuinely angry reply back.

sdr-move

Create a new skill called sdr-move.

Its job: work out my campaign move, then write three versions of it per segment

into Templates.

Be honest with me about the split: the move comes from knowing my buyer and you

cannot generate it from a prompt. What you CAN do is interrogate me, go and

listen, and refuse to accept a vague answer.

THE SHAPE OF A MOVE: find the thing they hate, fix it for free, inside software

they already pay for, mention what I sell at the end. Two tests before you

accept one: is it inside a tool they already own - because advice about my

product is a pitch and work done inside their stack is a gift; and could I

deliver it in under two minutes, a hundred times - because if it takes an hour

it is a service, not a move, and it dies in week two.

When I run it:

1. Ask me who I sell to and what I sell. Then go and listen: search where these

people complain in their own words - subreddits, forums, review sites, job

ads describing the grunt work. Bring back their actual phrasing, not a

summary. The complaint sentence is usually the subject line.

2. Then ask me the one question only I can answer: what unglamorous job is my

buyer doing badly right now, and what tool are they doing it in?

3. Offer three or four candidate moves. For each: the hated job, the tool it

lives in, the free thing I hand over, how long one takes to deliver. Say

which you would run and why. Then STOP and let me pick, or reject all four.

Never proceed on a move I did not actually endorse.

4. On my pick, write THREE versions per segment - three segments means nine

rows. Make them differ in KIND, not in wording, or the test is pointless:

v1 THE INTEREST OPEN. The subject line names the interest from Research

Notes. The body owns it in one line - that I looked them up, that this

is what a salesman does, and that I did it because what I have is

actually relevant to them. Then the free thing. Then one question.

v2 THE CONNECTION OPEN. Opens with the verified thing in common, stated

exactly as small as it really is. "We both worked at Acme, years apart"

- never "I see we're both connected to Dave", which reads as though I

am claiming to know them and draws the angriest replies there are.

Then the free thing, then one question.

v3 THE FORWARDED NOTE. An HTML email formatted as though I am forwarding

a short internal note asking me to reach out to this specific company,

with one line from me on top. Ask me WHO that note is from and what

they would really have said - the reason has to be one a real person

would actually give about this real company. If I have nobody to

forward from, ask whose request it genuinely is; if the honest answer

is nobody, drop this variant and tell me why rather than inventing

a person.

5. Draft each one, show it, take my edit. My wording wins every time - this

table is the voice the whole system imitates, and if it is your voice

rather than mine, every email downstream is subtly not me.

6. Write each approved row: Name, Channel = Email, Follow-up Level = 1st touch,

Segment (exact option, spelled identically to Prospects), Subject, and the

whole email in Examples. Leave Sent Count, Reply Count and Reply Rate alone.

7. Confirm rows per segment. Flag any segment with fewer than three - a segment

with one template learns nothing.

Shape of every version: about five lines, the free thing, one question, no

company talk. Never "I noticed" three times, never ask for fifteen minutes, and

never edit a template that already has sends - add a new row instead.

sdr-email

Create a new skill called sdr-email.

Its job: send today's first touches, one prospect at a time with my approval on

each, and log every send with the id that lets a reply be matched back to it.

Never send without showing me first.

When I run it:

1. Read sdr-stack-setup.md for my table layer, MY SENDING ROUTE and my daily

cap per mailbox. If the route is not recorded, ask which of the four it is

and write it into that file before doing anything else:

A GMAIL API DIRECT - service account with domain-wide delegation

B API LAYER - Unipile, EmailEngine or Nylas over my own mailboxes

C TURNKEY REST - a provider with its own send endpoint

D SMTP - warmed infrastructure driven over plain SMTP

2. Refuse to send if the deliverability gate is not met, naming what is

missing: a sending domain that is not the one my customers write to, SPF and

DKIM and DMARC on it, two weeks of warmup, a 20-50/day cap per mailbox, and

an unsubscribe line plus a postal address in every email. Offer to do

everything except send.

3. Find prospects where Stage = Enriched. For each, find Templates rows where

Channel = Email, Follow-up Level = 1st touch, and Segment matches this

prospect's Segment EXACTLY.

4. From those, pick in this order:

a. If any matching template has a BLANK Reply Rate, pick a blank one - every

version must be sent enough times to earn a score.

b. Otherwise pick the highest Reply Rate.

Rule (a) is the important half. Without it the system locks onto whichever

version got lucky in week one and never tells me it stopped learning.

5. If NO template matches: skip that prospect and tell me. Never send a

generic email - a missing template is a missing decision, not a gap to fill.

6. Write this one. Read the chosen template's Subject and Examples and write a

fresh version for THIS person in that style, working in ONE concrete detail

from Research Notes. One detail, not three - three is where "I noticed...

I noticed... I noticed" comes from. Shorter than the template, and never mention a template exists.

7. Show me the subject and the body. Wait. On my approval, send by my route,

rotating across my mailboxes and stopping at each one's daily cap:

A  base64url the RFC-822 message, POST it as "raw" to

users/{mailbox}/messages/send with a token impersonating that mailbox.

Keep the id and threadId returned.

B  POST the send endpoint with the mailbox's account id, recipient, subject

and body - recipients may need to be objects, not strings. Keep the id

returned AND the RFC-822 Message-ID, which is what replies join on here.

C  POST the provider's send endpoint; keep its messageId and threadId.

D  Send over SMTP with that mailbox's credentials, generating the

Message-ID yourself so you know it.

If my route can only draft, create the draft, say plainly it is in Drafts

for me to send, and do NOT report it sent. A route that only sends campaign

templates cannot run this system - stop and tell me.

8. Log it. Add a row to Sends: Prospect (link), Template (link), Channel =

Email, Sent At = now, Mailbox = the one you sent from, and the THREAD ID -

or, where my route has none, the RFC-822 Message-ID, noting in

sdr-stack-setup.md which of the two my rows hold. Then set Stage =

Contacted, verifying that write before moving on.

This id is the only way a reply can be matched back to the email that earned

it; a send logged without one can never score. If your send call returns it

under an unexpected field name, record the real one in sdr-stack-setup.md.

9. Stop at my cap. Report: sent or drafted per mailbox, skipped and why, and

how many remain at Enriched.

sdr-track

Create a new skill called sdr-track.

Its job: find out who actually wrote back, mark it, and let the scoreboard move.

When I run it:

1. Read sdr-stack-setup.md for my sending route and for whether my Sends rows

hold thread ids or RFC-822 Message-IDs. Find every row in Sends where

Replied is unchecked. Those are the only rows you touch - rows already

marked replied are finished. If there are none, say so and stop.

2. For each row, find any new message FROM THE PROSPECT sent after that row's

Sent At time, using the join my route actually supports:

A  users.threads.get on the stored threadId, from that mailbox.

B  Match each inbound webhook event's in_reply_to Message-ID against the

Message-ID I logged for the send; with no webhooks, list inbound mail

for that mailbox since the send and match the same way. Standard email

threading is the join - there is no proprietary thread id here.

C  Fetch the thread by its stored threadId from the provider's inbox API.

D  Fetch over IMAP, matching In-Reply-To and References against my logged

Message-ID.

Never match on the email address alone. People reply from aliases, forward

you to a colleague, and reuse subject lines. If a row has no id at all it

cannot be checked - collect those and report them as broken rows. That is a

logging bug in the send step, not something to guess around.

3. ONLY A HUMAN REPLY COUNTS. Read each message; do not just count messages.

Ignore out-of-office and vacation autoresponders, delivery-status

notifications, bounce-backs, unsubscribe confirmations, and anything whose

headers carry Auto-Submitted or Precedence: bulk. If my route tells me who

sent a message - some report whether it came from the API or from the human

on their phone - use that too, and never count something I sent myself.

One out-of-office logged as a reply inflates that version's score, and the

send step then picks the wrong winner on every run after that. A single bad

row poisons the whole loop.

4. For each real human reply: tick Replied, set Replied At, and set that

prospect's Stage = Replied so nothing else in the system touches them again.
5. NEVER CALCULATE REPLY RATE YOURSELF. Reply Rate is computed on the Templates

table and it updates itself the second Replied is ticked. If you find

yourself about to write a number into a score field, stop - you are about to

overwrite something that was right.

6. Report, in this order:

a. Who replied since last time: prospect name and one line of what they

said, so I can go and answer them.

b. Anything that bounced, listed separately, with the mailbox it bounced

from. A cluster from one mailbox is a deliverability problem, not a copy

problem, and it means pause that mailbox and go back to warmup.

c. THE SCOREBOARD. Every template with at least 5 sends: name, segment, sent

count, reply count, reply rate - ranked, highest first. Then the ones

still under 5 sends, listed as "not yet scored".

7. Only when every version in a segment has cleared 5 sends: name the winner and

the loser in that segment, quote the single weakest LINE in the loser, and

say what the winner's equivalent line does differently. One line, not the

whole email. If nothing has cleared 5 sends, say so and tell me to keep

sending. Never invent an opinion from three data points.

Rules: this skill never writes to Templates and never edits an email. It reads

threads, ticks boxes, and reports. Put it on a daily schedule - it is pure

bookkeeping, and it is the only skill here that should run without me.

sdr-reply

Create a new skill called sdr-reply.

Its job: REVIEW the reply I have written before I send it. Not write it - review

it.

The failure this exists to catch: the email offered something free. A stranger

answered with three words, "oh this is great". And the reply goes out with the

free thing AND a paragraph about the product AND the integrations AND what most

customers see. Then nothing, ever. Someone put their hand up for free help and a

brochure turned up. That is a bait and switch even when nobody meant it as one.

THE RULE EVERYTHING HERE CHECKS AGAINST: the only goal of any reply is the next

reply. Not the meeting, not the close. Do not think five messages ahead. On

every message the only question is what is most likely to get this person to

write back one more time.

When I paste their reply and my draft:

1. LENGTH. Count their lines and count mine. If they wrote six words and my

draft is eleven lines, say that first - it is the whole finding. Mirror

their length and their register. They do not know me, so I work them in

slowly, and the fastest way to do that is to sound like them.

2. THE PITCH CHECK. Does my draft mention the product, the features, the

results or the company at all, when they did not ask? If yes, quote the

exact sentence and cut it. This is the failure, not a stylistic quibble.

3. THE ASK. Does it end on something easy to answer? A question they can reply

to in one line beats a question that needs thought, which beats no question

at all, which beats a calendar link.

4. DELIVER THE FREE THING. If they said yes to the offer, the free thing has to

actually be attached, or promised with a time. "Here you go" then a

question. That is the shape.

5. PRESCRIBE ONE CHANGE. Rewrite the single weakest line and show me the before

and the after. Do not rewrite the whole message - my voice is the asset, and

every line you replace is a line that is no longer mine.

Read the thread before you judge the draft. Pull my previous replies to this

person and past threads that turned into calls, so you compare me against my own

winners rather than a generic ideal.

If I explicitly ask you to draft instead of review, the whole instruction is:

read the prospect's reply, mirror their length and style as closely as possible,

end on something easy to answer, do not pitch, do not list features, do not

mention what we sell unless they asked. Then tell me to change one line first.

Rules: if I start pasting your drafts unedited, say something. A reply that

sounds like a machine is exactly what this whole system was built to avoid, and

it degrades slowly enough that nobody notices until the replies stop coming.

Do not log anything here. sdr-track already moved this prospect to Replied; if

I want a note of what landed, append it to their Research Notes, never to

Sends, which is a send log and not a conversation log.
